# Operator capture and one-second commissioning requirements

Release 1.4.7 connects the gross Capture button and Save through `standard-capture.js` and Electron IPC. Standard mode freezes a stable scale receipt and three recent camera values after an operator confirms one truck. It expires after 30 seconds or device changes. Pending network saves use a durable journal and retry the identical request ID and data after restart. This mode does not establish exposure times, measurement times, or one-second synchronization. The strict one-second modules below remain prototypes, not enabled in the UI.

## Supplied DS-TCG406-E datasheet

The supplied `DS-TCG406-E_Datasheet_20260811.pdf` describes forward/backward plate recognition, video/coil/radar triggers, JPEG capture and a capture-time picture overlay (page 2); ISAPI, NTP and Ethernet (page 3); three trigger inputs (page 4); and Tanzania among the regions supported across baseline and customized variants (page 5). It does not establish this unit's manual-trigger API support, container OCR, capture-time precision, clock accuracy, timestamp metadata, or the correlation between an image and its physical exposure. The camera supplier must confirm these for the actual firmware and regional build. The supplied datasheet says IEEE 802.3af PoE (page 5); an older published DS-TCG406-E datasheet states 802.3at, so confirm the precise shipped model and power requirements with the supplier.

The combined simulator exercises a mock serial port, two simulated ISAPI camera responses and real local OCR on a test image. Its clock bounds and timestamps are invented by the test; they are not device measurements and must not be used to enable production capture.

The supplied integration write-ups propose multipart ANPR events with a `dateTime`, UUID and picture references. One sample had mismatched XML tags; the later sample parses, but its origin and firmware are not established. A TCG integration-guide example uses whole-second timestamps; a fractional timestamp in an example does not establish installed-device timing accuracy. The `src/hikvision-event.js` and `src/hikvision-multipart.js` prototypes validate metadata and match an in-memory JPEG against its scene-image reference. They do not authenticate senders, establish that the event was caused by the requested trigger, prove exposure time, or run in the app's capture/save path. The actual trigger behavior, an event and image from each installed camera, and measured clock and scale timing remain necessary. A snapshot request alone is not evidence that the container-camera event delivers an image when no plate is visible.

## Intended workflow

1. A single vehicle occupies a controlled capture zone; the operator confirms it is fully on the scale and presses Capture. The maximum acceptable exposure-to-weight difference is one second, including measured timing uncertainty.
2. The software reads a fresh stable physical scale sample and assigns a unique capture-session ID. It requests front and rear manual ANPR results and a container image concurrently.
3. Each response must be tied to that request and include trustworthy physical acquisition timing, independently measured clock uncertainty, and an event identifier. The snapshot acquisition time must not be confused with OCR completion time or HTTP response arrival time.
4. Reject the entire session if any response is missing, ambiguous, duplicated, out of tolerance, insufficiently precise or from an uncertain clock; reject if scale data becomes stale, unstable, disconnected, or belongs to a changed vehicle cycle. Do not use a cached reading as a substitute.
5. Re-check the scale and occupancy before accepting the data. Store the weight sample time, each source's event ID and capture time, timestamp resolution, uncertainty, configured tolerance, and capture-session ID with the record. Images remain transient unless explicitly authorized.

## What must be verified before integration

- The chosen maximum timing skew is one second; zero skew and zero recognition error cannot be guaranteed by HTTP, ordinary cameras, OCR or a scale serial stream. If timestamp resolution and verified uncertainty cannot establish this bound, reject the capture.
- Verify the exact DS-TCG406-E firmware supports the manual-trigger endpoint and returns the documented plate, capture timestamp and unique image ID. The generic Hikvision documentation alone does not prove this for a specific unit.
- Establish the accuracy and precision of camera clocks and the scale's acquisition timestamp. A PC receive timestamp is not proof of the scale's physical measurement time. Synchronize clocks to an agreed local source and measure residual error.
- Establish how the third camera's JPEG snapshot exposes or can be associated with its actual exposure time. HTTP response time is not a reliable exposure timestamp; this is a current blocking gap.
- Confirm the scale indicator model, RS-232 frame structure, stable indicator and timestamp/trigger capabilities; measure processing and transport delays.
- Define reliable single-vehicle lane control, camera fields of view and operator procedure. A one-truck rule reduces risk but does not mathematically prove three identifiers belong to the same vehicle.
- Exercise real equipment and adversarial cases: wrong or two vehicles in view, missed or delayed frames, timestamp drift, network interruption, stale messages, camera restart, OCR errors, changed or unstable weight, zero return, retries and duplicate events. Validate with measured timing evidence before releasing.

`src/hikvision-manual.js`, `src/capture-session.js`, `src/capture-coordinator.js`, `src/operator-capture.js`, `src/capture-transaction.js`, and `src/capture-gross-request.js` are isolated prototypes exercised by mocks. The transaction manager copies only device evidence, rejects duplicate or expired sessions, rechecks device state, and consumes a capture before starting a save; if a save fails ambiguously the caller must reconcile by the same request ID, not silently create another record. Camera requests receive an abort signal on timeout or failure, but each adapter must honor it. The event-replay guard is in-memory only; durable replay prevention across restart is still required. An invalidation cannot undo a save request already sent to the server. None is connected to the current app's save path. Their caller is responsible for verifying event origin, clock uncertainty, actual exposure times, stable-weight continuity, occupancy and lifecycle. Session IDs attached by software alone are not hardware proof.

Local website changes accept an optional capture-evidence object, check consistency with the reported weight, three identifiers, request ID and timing bounds, and write the sanitized metadata into the existing audit record under `capture_evidence_unverified`. They reject conflicting evidence on a repeated request ID and do not accept images in the evidence object. This is validation of what the client reports, not device authentication or independent proof of timing. The current app does not send this object and does not send this evidence in standard mode. Standard mode instead sends `capture_workflow`, audited as `capture_workflow_unverified` with receipt timestamps and operator confirmation. Server request fingerprints reject changed retries.
